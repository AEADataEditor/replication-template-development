# Development instructions for replication-template-development

This file applies when working on this repository itself (the template's
pipelines, automations, tools, and docs). It is NOT deployed: the deploy
workflow replaces it with [build/CLAUDE-deployed.md](build/CLAUDE-deployed.md),
which holds the instructions for the replication/transparency-editor role used
in each `aearep-NNNN` repository (where the `.claude/skills/` skills run).
Put editor-role instructions there, not here.

## Coding Conventions

- Keep `bitbucket-pipelines.yml` steps short: call into `automations/*.sh` rather than writing multi-line inline logic in the YAML.
- When an automation needs real logic beyond argument/ticket resolution and shell plumbing (API calls, parsing, data transforms), pair a thin `automations/NN_name.sh` (resolves arguments/the Jira ticket, calls the tool) with a `tools/name.py` that does the actual work. Examples: `70_publish_comment.sh`->`jira_add_comment.py`, `30_download_commit_jira_attachments.sh`->`jira_download_attachments.py`, `26_update_jira_software.sh`->`jira_update_software.py`. Don't add a wrapper script whose only job is to call another script that already does the work - extend that script instead.
- Never write or run inline Python (`python3 -c "..."`) in the pipeline YAML or in shell scripts, under any circumstances. Always put it in a proper file under `tools/`.
- Unit tests for `tools/*.py` scripts live in a top-level `tests/` directory (NOT under `tools/`), named `test_<script>.py` (e.g. `tools/jira_add_comment.py` -> `tests/test_jira_add_comment.py`). Run one directly with `python3 tests/test_<script>.py`. Each test file resolves the module under test via `sys.path.insert(0, os.path.join(os.path.dirname(os.path.dirname(os.path.abspath(__file__))), "tools"))` so it can `import <script>` from `tools/`. `tests/` is excluded from the deployment rsync in `.github/workflows/deploy.yml`, so it never reaches the public template - keep it that way.
- Pipeline steps that need the deposit directory source `tools/resolve_project_id.sh` (sets `projectID` and the repository ID variables) instead of re-deriving it inline. When adding a repository, extend that script, and give the downloader a network-free `--dir-name` option it can call.
- Every script in `automations/` has its own page in `docs/automations/` (named `96-92-<script stem>.md`, starting with the label `(help-<script stem>)=` and an H1 title), listed in `docs/myst.yml` under "Automation scripts". Each page carries, right below the H1, an `{attention}` admonition saying the script is normally run by a Bitbucket pipeline, with links to every pipeline step and `bitbucket-pipelines.yml` line that calls it, and to other automation scripts that call it. Never write or edit that block by hand: it is generated by `python3 tools/automation_doc_links.py` between the `BEGIN/END pipeline-callers` comments. Always rerun the tool when you add or rename an automation script or its doc page, add or rename a pipeline, or edit `bitbucket-pipelines.yml` or an `automations/*.sh` call (line numbers shift), and commit the updated pages with the change. A new pipeline also needs a `(pipeline-<name>)=` label on its section in `docs/automations/96-92-bitbucket-pipelines.md`. `python3 tools/automation_doc_links.py --check` (also run by `tests/test_automation_doc_links.py`) fails when a page, a label, or a link is missing or stale.
- `docs/` is end-user documentation only (it is published as a MyST site; `docs/superpowers/**` is excluded from that build and is exempt from this rule). Never let testing content - manual QA/testing plans, "Testing"/"Testing plan" sections, references to `tests/test_*.py` - live in a `docs/` page. When a tool's doc page under `docs/tools/**` or `docs/automations/**` needs a testing section, split it: keep usage/behavior docs in `docs/`, and put the testing plan in `tests/testing-plan-<script>.md` (e.g. `docs/tools/repository/96-90-sbatch-shell.md` -> `tests/testing-plan-sbatch-shell.md`). Cross-link between the two rather than duplicating content.
- Every help page under `docs/tools/**` and `docs/automations/**` (except `index.md`) ends with a `{seealso}` admonition showing the small GitHub logo (`docs/images/github-mark.svg`, sized by the SVG itself - no `{height=...}` attribute, MyST prints it literally) and a link to the documented script on GitHub (`AEADataEditor/replication-template`, branch `master`). Never write or edit that block by hand: it is generated by `python3 tools/doc_source_links.py` between the `BEGIN/END source-link` comments. Rerun the tool whenever you add or rename a doc page or its script, and commit the updated pages; `python3 tools/doc_source_links.py --check` (also run by `tests/test_doc_source_links.py`) fails when a page is missing the block, is stale, or has no matching source file. For a page whose name doesn't match its script, add it to `SPECIAL` in the tool.
